# 작업 1~9 리뷰와 실동작 수정 (2026-08-26)

> 로드맵 문서의 작업 1~9(문서 동기화 ~ DealGroup UI)가 머지된 시점의 리뷰.
> **코드를 읽는 데 그치지 않고 실제로 기동해 수집시킨 뒤** 확인한 결과다.

## 1. 한 줄 요약

구조는 로드맵을 충실히 따랐지만, **머지된 두 기능이 실데이터에서 0%로 동작하지 않고 있었다.**
단위 테스트는 전부 통과했는데도 잡히지 않았다.

## 2. 잘된 점

- `SourceCollector` + `PagedCollectionSupport` + 출처별 Properties로 작업 4·5가 깔끔하게 반영됨
- `DealGroupingService`가 보수적으로 설계됨 — 같은 출처 후보가 여럿이거나 기존 그룹이 충돌하면
  그룹화를 건너뛰고 경고를 남긴다("false positive가 false negative보다 나쁘다" 준수)
- `uk_deal_group_source`(그룹당 출처 하나) 유니크 제약 — 문서에 없던 좋은 정합성 장치
- 대표 딜 선정 점수(productUrl 4 > price 2 > thumbnail 1 > 최신)가 로드맵 10.4와 일치
- `NewDealDetailSupport`가 신규 딜만·횟수 제한·실패 격리로 출처 부담을 통제
- docs/03·04 갱신과 작업 6 조사 노트까지 남아 문서 규율이 지켜짐

## 3. 발견한 문제

### 3.1 퀘이사존 상품 URL 확보율 0% — 상세 요청이 순수 낭비

`QuasarzoneDetailParser`가 상세 표의 `<th>링크</th>` 행을 찾는데, **현재 페이지에는 그 행이 없다.**

- 상세 페이지 표본 **7건 전부**에 `링크` 행 없음. 헤더는 `판매처 / 가격 / 배송비·직배`뿐
- 작업 6 조사 노트의 표본 글(1968628)조차 지금은 `판매처 / 가격`만 있다 → **사이트 구조가 바뀐 것**
- 실제 상품 URL은 본문에 있고, 본문 원본은 `textarea#org_contents`에 들어 있다
  (화면의 `.view-content`는 스크립트가 채우기 전까지 비어 있어 서버 HTML에서는 빈 껍데기)

결과: DB 실측 `product_url` **0건**. 매 주기 상세 요청 3건을 쓰면서 아무것도 얻지 못하고 있었다.

### 3.2 교차 출처 dedup이 구조적으로 발화 불가 — 그룹 0건

`findCrossSourceCandidates`가 **`titleNormHash` 정확 일치로만** 후보를 뽑았다.
그래서 `isStrongMatch`의 상품 URL 경로도 *제목 해시가 같아야만* 도달할 수 있었다.

로드맵 10.2는 URL을 "매우 강한 일치"로 두는데, 구현은 가장 약한 신호(제목 완전 일치)를
관문으로 쓴 셈이다. **후보 탐색(retrieval)과 판정(scoring)을 분리하지 않은 것이 원인.**

실측: 교차 출처 해시 일치 **0건**, `deal_group` **0건**.
그런데 그룹 대상은 실제로 존재했다:

| 퀘이사존 | 루리웹 |
| --- | --- |
| `[기타] 더 위쳐3 콘서트 영상 무료 소장` | `[GOG] 위쳐 3 콘서트 영상 무료` |
| `[네이버] (품절) 컬쳐랜드 문화상품권 5만원권` | `[네이버] 컬쳐랜드 5만상품권 (46,500원/무료)` |
| `[네이버] 메가커피 23% 할인 딜 (네이버멤버십)` | `[네이버멤버십] 메가커피 아메리카노 외` |

작성자가 다르니 제목이 같게 정규화되는 일은 드물다. 제목 일치를 전제로 하면 사실상 안 걸린다.

### 3.3 과거 데이터 백필 수단 없음

새 컬럼(`shop_name`, `product_url`, `comment_count`, `title_norm_hash`)은 재수집 목록(1페이지)에
걸린 딜만 채워진다. 그 이전 딜은 영원히 null이고 dedup 후보 풀에서도 빠진다.

### 3.4 작업 2~9가 실DB에서 한 번도 안 돌았음

리뷰 시점의 로컬 DB에는 `deal_group` 테이블도, 새 컬럼도 없었다. 픽스처 단위 테스트는
전부 통과했지만 `product_url 0건`·`group 0건`을 아무도 보지 못했다.

## 4. 이번에 수정한 것

### 4.1 퀘이사존 상세 파서에 본문 폴백 추가

`링크` 행이 없으면 `textarea#org_contents`(본문 원본)를 파싱해 **첫 외부 링크**를 상품 URL로 쓴다.
페이지의 배너·후원사 링크와 섞이지 않도록 범위를 본문 안으로 좁혔다.
기존 `링크` 행 경로는 그대로 두어 회귀가 없다.

**검증**: 퀘이사존 `productUrl` **0/29 → 2/29**. 저장된 값도 실제 상품 URL이었다
(`http://ssg.li/...`, `shopping.naver.com/festa/...`).

### 4.2 dedup 후보 탐색을 상품 URL로 확장

`findCrossSourceCandidatesByProductUrl`을 추가하고, `DealGroupingService.findCandidates`가
**상품 URL 일치와 제목 해시 일치를 각각 독립적으로** 훑도록 바꿨다(판정 로직은 그대로).

테스트 추가: "제목 표현이 서로 달라도 상품 URL이 같으면 그룹화한다".

### 4.3 필드 확보율 로그

`DealUpsertSupport`가 수집 회차마다 남긴다:

```
수집 필드 확보율 [quasarzone]: price=29/29 shop=29/29 productUrl=2/29 thumb=29/29 comments=27/29
수집 필드 확보율 [ruliweb]:    price=3/28  shop=28/28 productUrl=0/28 thumb=0/28  comments=25/28
```

파서 선택자는 사이트 구조가 바뀌면 예외 없이 조용히 null이 된다. 이번 건이 정확히 그 사례라
수치로 감시한다.

## 5. 남은 것

- **상품 URL 확보율이 여전히 낮다.** `max-detail-requests: 3`(주기·출처당)이 병목이고,
  상세 보강은 **신규 딜에만** 적용되므로 기존 240여 건은 계속 null이다.
  → 그룹화는 아직 0건. 구조적 장애물은 없어졌지만 **커버리지가 남은 제약**이다.
- 루리웹 가격 확보율 3/28. 제목 관례가 제각각이라 의도적으로 보수적인 결과다.
- 백필 방법(과거 딜 상세 보강)을 할지 말지 결정 필요. 출처 부담과 맞바꾸는 판단이다.

## 6. 로드맵 문서에 반영하면 좋을 점

1. **완료 조건에 실데이터 수치를 넣는다.** 지금은 "테스트 추가·문서 갱신·프론트 확인" 수준이라
   픽스처만 통과하면 끝난다. 이번 두 문제가 정확히 그 틈으로 빠져나갔다.
2. **후보 탐색과 판정을 분리하라고 명시한다.** 10.2에 신호 우선순위는 있지만 *무엇으로 후보를
   검색할지*가 없어서 구현이 제목 해시를 검색 키로 썼다.
3. **Phase 4 착수 전제조건을 수치로 건다.** 상품 URL이 사실상 0인 상태로 dedup이 머지됐다.
4. **21장 지표를 각 작업 완료 조건으로 앞당긴다.** 확보율은 로컬 1회 수집으로도 측정된다.
5. **외부 마크업의 취약성을 원칙으로 넣는다.** 조사 노트가 사흘 만에 실제와 어긋났다.
