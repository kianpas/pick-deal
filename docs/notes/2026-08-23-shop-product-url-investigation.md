# Shop / Product URL 조사

> 조사일: 2026-08-23
> 범위: Quasarzone·Ruliweb 목록 fixture와 소수의 실제 상세 페이지
> 목적: 스키마를 먼저 만들지 않고 구매 링크의 확보 가능성·신뢰도·요청 비용을 확인한다.

## 1. 결론

- 두 출처 모두 **목록 HTML만으로는 게시물별 상품 URL을 얻을 수 없다.** 현재 목록 Parser가 가져오는 URL은 커뮤니티 원문 게시글 URL이다.
- 두 출처 모두 상세 페이지에는 광고·메뉴 링크와 구분 가능한 전용 위치가 있다.
  - Quasarzone: 상세 정보 표의 `링크`와 `판매처`
  - Ruliweb: 본문 아래 `.source_url` 영역(본문의 첫 링크와 같은 값인 표본 확인)
- 후속 논의에서 화면에 판매몰도 함께 표시하기로 결정해 작업 7의 최소 범위를 nullable `shopName`과 `productUrl`로 확정했다. `shopName`은 출처 표기를 그대로 저장하고, `originalUrl`은 커뮤니티 원문 링크로 계속 유지한다.
- 수집 시 쇼핑몰 최종 URL까지 매번 따라가지 않고, 출처 상세 페이지가 명시한 외부 URL을 그대로 저장한다. 이 방식은 redirect 요청을 추가하지 않으며 출처가 제공한 제휴·단축 링크도 보존한다.
- `canonicalProductUrl`, `shopProductId`, 별도 Shop 엔티티는 이번 표본만으로 일반화하지 않는다. 알려진 판매처별 규칙이 실제로 필요해지는 교차 출처 dedup 작업에서 다시 판단한다.

## 2. 현재 데이터 의미

| 값 | 현재 의미 | 상품 링크로 사용 가능 여부 |
| --- | --- | --- |
| `deal.original_url` | Quasarzone/Ruliweb 원문 게시글 | 불가 — 의미를 바꾸지 않는다 |
| 제목의 `[판매처]` | 작성자가 입력한 판매처 문자열 | 보조 정보 — 오탈자·`기타`·복수 판매처 가능 |
| 목록 행의 외부 링크 | 게시글 링크·이미지·필터·광고가 혼재 | 불가 |
| 상세의 전용 링크 영역 | 작성자가 등록한 구매/출처 링크 | `productUrl` 후보 |

## 3. 출처별 조사 결과

### 3.1 Quasarzone

목록 fixture의 딜 행에는 썸네일과 원문 게시글 링크가 있고, 페이지 전체에는 쇼핑몰 필터·배너 링크가 다수 있다. 이 링크들은 특정 Deal의 상품 URL이 아니므로 목록에서 상품 URL을 고르면 안 된다.

상세 표본:

- 원문: `https://quasarzone.com/bbs/qb_saleinfo/views/1968628`
- 제목: `[쿠팡] 오리코 PD 100W SD/TF 리더 M.2 SSD 외장하드 케이스`
- 상세 정보 표:
  - 판매처: 쿠팡
  - 표시 URL: `https://www.coupang.com/vp/products/9320059618?vendorItemId=95248275824`
- 클릭용 `href`는 `javascript:goToLink(base64...)` 형태지만, 같은 `<td>`의 표시 텍스트와 페이지 스크립트에는 원본 URL이 존재한다.
- 페이지는 구매 링크가 제휴 링크로 전환될 수 있음을 명시한다.
- 표본 URL을 직접 확인했을 때 redirect는 없었지만 HTTP 403을 반환했다. URL 구조에서는 상품 ID `9320059618`과 vendor item ID를 식별할 수 있으나, 응답 성공 여부를 수집 필수 조건으로 삼으면 안 된다.

판단:

- 전용 표의 링크 텍스트를 추출하면 광고 링크와 구분할 수 있다.
- JavaScript를 실행하거나 base64 인자를 해석하는 방식보다, 전용 표의 표시 URL을 읽는 방식이 단순하고 안정적이다.
- 짧은 시간에 상세 표본을 연속 조회한 조사 경로에서 HTTP 429가 관측됐다. 운영 수집에서는 모든 기존 Deal의 상세를 매 주기 다시 요청하면 안 된다.

### 3.2 Ruliweb

목록 fixture에는 원문 게시글 링크만 있으며 구매 URL은 없다. 상세 페이지에는 본문 외에 `.source_url` 영역이 있어 페이지 전체의 광고 링크와 구분할 수 있다.

표본 A:

- 원문: `https://bbs.ruliweb.com/market/board/1020/read/106481`
- 제목: `[롯데온] 스위치2+스플래툰 레이더스+ 아미보 / 730900원`
- 출처 URL: `https://s.lotteon.com/xt85P9DdUQ`
- 본문 링크의 실제 `href`는 Ruliweb 경유 URL이지만 `ol` 파라미터와 표시 텍스트에 위 단축 URL이 들어 있다.
- 단축 URL은 redirect 1회 후 롯데온 상품 URL로 이동했다.
- 최종 URL에서는 상품 후보 ID `LO2745512180`과 옵션 후보 `sitmNo`를 확인할 수 있었다.

표본 B:

- 원문: `https://bbs.ruliweb.com/market/board/1020/read/106479`
- 제목: `[카카오] 스위치2 +포켓몬za 727,725원`
- 출처 URL: `https://store.kakao.com/nintendo/products/739338752?ref=SHARE`
- 본문 첫 링크와 `.source_url` 값이 같고 URL 경로에서 상품 후보 ID `739338752`를 확인할 수 있었다.

판단:

- `.source_url a`의 표시 URL 또는 목적 URL을 우선하면 광고·이미지 링크와 구분할 수 있다.
- Ruliweb 자체 경유 URL을 저장하기보다 그 안의 `ol` 목적지 또는 `.source_url`이 표시하는 외부 URL을 저장하는 편이 출처 의도에 가깝다.
- 직접 상품 URL과 쇼핑몰 단축 URL이 모두 존재하므로 수집 단계에서 일률적인 canonical URL을 만들지 않는다.

## 4. 신뢰도 기준과 사용처

여기서 신뢰도는 링크의 인기나 판매처 평판이 아니라 **해당 게시글이 소개하는 상품·행사로 사용자를 정확히 보낼 가능성**이다.

| 등급 | 판단 기준 | 자동 저장·노출 | dedup 신호 |
| --- | --- | --- | --- |
| 높음 | 출처의 전용 링크 영역에 있고, URL이 유효한 HTTP(S)이며 제목의 판매처 또는 상품 맥락과 일치 | 가능 | 알려진 판매처 ID를 추출한 경우만 후보로 사용 |
| 보통 | 전용 영역이지만 단축·제휴·경유 URL이거나 상품이 아닌 기획전/검색 결과일 가능성이 있음 | 원본 URL 그대로 가능, 링크 성격을 과장하지 않음 | URL 자체를 동일 상품의 강한 키로 사용하지 않음 |
| 낮음 | 본문 임의 링크, 광고·이미지·댓글 링크, JavaScript만 있고 목적지를 확인할 수 없음, 제목 맥락과 불일치 | 자동 저장하지 않음 | 사용하지 않음 |

신뢰도는 다음 결정에 사용한다.

1. 화면에 `구매 링크`로 노출해도 되는지
2. 판매처명을 URL 도메인에서 보정해도 되는지
3. `shopProductId`를 교차 출처 dedup의 강한 신호로 사용할 수 있는지

작업 7의 단순 링크 제공에서는 **전용 링크 영역에 있는 유효한 HTTP(S) URL**까지만 자동 저장한다. 링크가 실제 단일 상품인지, 기획전인지까지 억지로 판정하지 않는다.

## 5. 추가 요청 비용

추가 요청 비용은 HTTP 요청 수가 중심이며 응답 시간·대역폭·차단 위험을 함께 뜻한다.

현재 Incremental 수집은 출처별 목록 1페이지이므로 기본적으로 출처당 1회 요청이다. 상세를 모든 목록 항목에 붙이면 다음처럼 증가한다.

```text
현재: 목록 1회
단순 상세 수집: 목록 1회 + 상세 최대 50회 = 출처당 최대 51회
Bootstrap: 목록 3회 + 상세 최대 150회 = 출처당 최대 153회
redirect까지 확인: 위 요청에 링크별 redirect 횟수 추가
```

따라서 구현 시에는 다음 제한이 필요하다.

- DB에 없는 신규 `externalId`만 상세 요청
- 기존 Deal은 `productUrl` 유무와 관계없이 재요청하지 않음
- 실행당 상세 요청 상한을 별도로 설정
- 상세 요청 실패가 목록 수집·Deal 저장을 실패시키지 않음
- redirect는 수집 중 따라가지 않고 원본 외부 URL을 저장

이렇게 하면 정상 운영에서는 새 글 수만큼만 상세 요청이 추가된다. 다만 Bootstrap에서는 신규 항목이 많으므로 초기 상세 요청 상한을 일반 수집보다 보수적으로 잡아야 한다.

## 6. robots.txt와 조사 한계

- Quasarzone robots.txt는 조사한 `/bbs/qb_saleinfo/views/{id}` 경로를 금지하지 않는다.
- Ruliweb robots.txt는 검색·필터 관련 경로를 제한하지만 조사한 `/market/board/1020/read/{id}` 경로는 금지하지 않는다.
- robots.txt 허용은 무제한 요청 허가가 아니다. 실제 429 관측을 운영 한도 설계에 반영해야 한다.
- 조사 시점의 표본은 Quasarzone 1건, Ruliweb 2건으로 작았다. 구현에서는 두 출처의 상세 fixture를 추가하고 전용 영역 추출 및 광고·본문 링크 제외를 테스트했다.

## 7. 작업 7 권고안

다음 작업은 MVP 범위에서 아래처럼 줄이는 것을 권장한다.

1. `deal.shop_name`, `deal.product_url` nullable 컬럼을 추가한다.
2. 판매몰 이름은 출처 표기를 그대로 저장하며 지금은 표준화하지 않는다.
3. 상세 Parser는 각 출처의 전용 링크 영역에서 HTTP(S) 외부 URL 하나만 추출한다.
4. `original_url`은 계속 커뮤니티 원문 링크로 유지한다.
5. 별도 Shop 엔티티, `canonical_product_url`, `shop_product_id`는 추가하지 않는다.
6. 신규 Deal만 실행당 출처별 최대 3건 상세 조회하고 실패 시 `product_url = null`로 저장한다. 기존 Deal 자동 backfill은 하지 않는다.

이후 교차 출처 dedup을 구현할 때 실제 수집된 URL 분포를 보고 판매처별 canonical 규칙과 상품 ID 추출기를 추가한다.
