## 1. 결론과 이 문서의 역할

현재 Spring Boot·Next.js·PostgreSQL 구조와 단일 앱 수집 방식을 유지합니다. 다음 개선은 문서 정합성, 실제 사용자 동작, 개인용 상시 운영 준비에 집중하는 것이 적절합니다.

이 문서는 **검토 시점의 근거 기록**입니다. 새로운 설계 명세나 두 번째 로드맵으로 사용하지 않습니다. 제안이 채택되면 해당 계약의 원본 문서에 반영하고, 진행 상태는 기존 roadmap에서만 관리합니다. 과거 기록을 계속 현재화하거나 모든 작업에서 필수로 읽게 할 필요는 없습니다.

유지할 결정:

- 출처(Source)와 판매처(shop), 원문 링크와 구매 링크의 분리
- 동일 출처 중복 방지 유니크 제약과 원본을 보존하는 DealGroup
- 출처별 Client·Parser·CollectService 및 실제 중복에 기반한 공통화
- HTML fixture 테스트와 실수집 결과 확인의 병행
- Redis·별도 worker·복잡한 상품 모델의 도입 보류
- 2026-09-01 결정인 과거 상품 URL 백필 및 가격 이력 제외

## 4. DealGroup 의도 확인과 배포 정책

### DealGroup — 출처 간 유사 딜 묶음

**사용자가 확인한 목적은 여러 사이트에 올라온 유사한 딜을 모아 보여주는 것입니다. 행사 재시작 여부를 판정하는 기능은 목적에 포함되지 않습니다.**

이 의도는 기존 roadmap에도 있습니다. 같은 상품이 여러 출처에 올라오면 목록에서 하나로 묶고 상세에서 출처를 보여줍니다. 행사 재시작 판정, 시간 제한, 조건 변경에 따른 자동 분리는 명시적 요구사항이 아닙니다.

| 구분 | 이번 확인 및 추천 방향 |
| --- | --- |
| 사용자 확인 목적 | 여러 출처의 유사 딜을 묶어 중복 열람을 줄이고 출처별 정보를 비교 |
| 그룹 기준 | 같은 구매 대상을 다루는지 우선 확인. 다른 모델·용량처럼 구매 대상이 달라지는 정보는 보존 |
| 원본 데이터 | 게시글과 출처별 관측 정보를 그대로 보존 |
| 가격·상태 변경 | 그 이유만으로 기존 그룹을 자동 분리하는 기능은 도입하지 않는 방향을 추천 |
| 행사 재시작·시간 제한 | 현재 필수 작업에서 제외. 실제 혼동 사례가 확인될 때만 검토 |
| 모호한 매칭 | 근거가 부족하면 별도 카드 유지 |

가격 차이는 카드 할인 적용 여부나 관측 시점 차이일 수도 있으므로 제품 목적상 반드시 다른 그룹이라는 뜻은 아닙니다. 다만 **현재 가격·판매처 정확 일치 규칙은 초기 오탐 방지 장치로 유지할 수 있습니다.** 이번 의도 확인을 근거로 코드의 판정 조건을 즉시 완화하지 않습니다. 함께 보고 싶은데 묶이지 않는 실제 사례를 확보한 뒤 조정합니다. 판매처가 다른 글까지 묶을지는 이번 대화에서 확정하지 않았습니다.

보완의 초점은 그룹 자동 분리보다 **대표 카드 정보의 일관성**입니다. 활성 게시글을 대표로 우선하고, 카드의 가격·구매 링크·상태가 같은 대표 게시글 기준인지 확인하는 방향을 추천합니다. 상세는 출처별 게시 시각·가격·상태를 구분합니다. 이는 새 추천 정책이며 현재 구현 완료를 의미하지 않습니다. 채택하면 docs/03·05의 그룹 상태 집계·대표 선택 정책을 함께 맞추고, 상세의 출처별 가격 노출에 필요한 응답 필드도 확인합니다.

또한 roadmap의 “그룹 0건은 규칙이 아니라 URL 커버리지 때문”이라는 단정은 완화해야 합니다. 가격·판매처도 필수 조건입니다. 후보 없음, 가격 없음, 판매처 불일치, 복수 후보 충돌을 구분해 원인을 확인합니다. 8월 26일 확보율은 역사적 측정값이며 현재 DB 결과가 아닙니다.

### 개인용 배포의 접근 범위

고정 user_id와 인증 없는 쓰기 API를 그대로 인터넷에 공개하면 다른 방문자도 같은 설정을 변경할 수 있습니다. `/internal` 경로명은 접근 제한이 아닙니다. 개인 접근을 제한한 배포를 우선하고, 공개 데모가 필요하면 조회와 개인 설정 변경의 접근 범위를 구분합니다. 회원가입 전체 구현을 이번 작업의 전제조건으로 삼지는 않습니다.

배포 완료 조건은 접근 제한, HTTPS, 실제 프론트 도메인의 CORS, prod/시드 분리, Flyway, DB 백업·복구 확인입니다. 브라우저도 백엔드를 직접 호출하므로 SSR 접속 성공만으로 통합 검증을 끝내지 않습니다.

## 5. 기존 문서에 반영하는 방법

1. 문서 정합성 수정은 별도 작업으로 처리합니다. 코드·인프라 개편을 함께 시작하지 않습니다.
2. 채택한 정책은 소유 문서에만 반영합니다. 요구사항은 docs/01, 구현 구조는 docs/02, API는 docs/03, 스키마는 docs/04, 수집·그룹 규칙은 docs/05, 배포는 docs/06입니다.
3. roadmap에는 이 리뷰 링크와 채택한 후속 작업·완료 조건만 짧게 남깁니다. 본문의 분석을 복사하지 않습니다.
4. 진행 상태는 roadmap에서만 갱신합니다. 이 문서는 당시 검토 기록으로 보존합니다.

### 로드맵 축소도 문서 정합성 작업에 포함

이 리뷰를 구현 지침으로 적용할 때는 **기존 roadmap을 축소·정리하는 작업을 명시적으로 포함**합니다. 리뷰 파일을 추가하는 것만으로 roadmap이 자동으로 줄어드는 것은 아닙니다.

| 유지할 내용 | 줄이거나 이동할 내용 |
| --- | --- |
| 프로젝트 목적과 현재 상태 요약 | 여러 장에서 반복하는 목적·우선순위 설명 |
| 완료·진행·보류를 보여주는 단일 작업 표 | 완료 작업 1~9의 상세 실행 지시와 오래된 첫 요청 예시 |
| 다음 작업의 범위·완료 조건 | docs/01~06에 이미 있는 API·스키마·수집 규칙의 중복 설명 |
| 백필·가격 이력 제외 등 채택된 결정과 이유 | 미채택 점수식·미래 아키텍처의 상세 예시 |
| 필요한 설계·리뷰 기록 링크 | 여러 곳에서 반복하는 상태표와 최종 요약 |

완료 작업은 상태표와 기존 notes 링크로 남깁니다. 보존 가치가 있는 근거만 notes로 이동하고 단순 중복은 삭제합니다. 문서를 잘게 쪼개 새 파일 수만 늘리지 않습니다. 미래 기능은 방향 한 문단 수준으로 남기고 과거 탐색 예시를 현재 필수 구현 규칙으로 취급하지 않습니다.

추천 순서는 문서 정합성 → 목록 상태·데모 UI·모바일 동작 → 개인용 상시 운영 → 운영 데이터에 근거한 조회·수집·그룹 개선입니다. 기존 로드맵의 OCI 배포 방향을 유지하며, 본문 제안을 모두 배포 선행조건으로 확대하지 않습니다.

## 불확실성 지도

- 프론트 상태 결함은 정적 분석 결과이며 실제 브라우저 재현이 필요합니다.
- 메모리 조회의 병목 시점은 실측이 필요합니다. 그룹 시간 제한은 현재 필수가 아니며 필요성이 확인될 때만 검토합니다.
- 다른 판매처·다른 가격까지 허용하는 매칭 범위와 대표 카드 정책은 추천과 사용자 확정 의도를 구분해 채택해야 합니다.
