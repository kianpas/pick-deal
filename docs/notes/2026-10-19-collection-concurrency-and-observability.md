## A. 그룹화 경합

**문제.** 그룹화는 다른 출처 후보를 조회한 뒤 연결한다. 앱 스케줄러와 원격 수신처럼 다른 출처의 저장이
동시에 실행되면 READ COMMITTED에서 서로의 미커밋 Deal을 보지 못한다. 기존 `synchronized`는 원격 수신끼리만,
한 JVM 안에서만 직렬화했다.

**재현(PostgreSQL 17, Testcontainers).** 두 트랜잭션이 저장 후 커밋 전에 서로를 기다리게 해 겹침을 고정했다
(`CollectionWriteConcurrencyTest`). 수정 전 결과:

1. 같은 상품의 두 신규 Deal이 동시에 저장되면 둘 다 그룹 없이 남았다.
2. 두 출처가 동시에 같은 기존 Deal C와 일치하면 그룹이 둘 생기고 C는 나중 커밋 쪽 그룹으로 덮어써졌다.
   한 신규 Deal은 C와 다른 그룹에 남았다.

1은 이후 재수집에서 회복될 수 있지만 수집 범위를 벗어나면 남는다. 2는 DB 제약(`uk_deal_group_source`)으로도
잡히지 않는 정합성 오류다.

**해결.** 그룹 판정 시작 시 PostgreSQL 트랜잭션 advisory lock(`DealGroupingLock`)을 잡아 커밋까지 유지한다.
뒤 트랜잭션은 잠금을 기다린 뒤 새 쿼리에서 앞 트랜잭션의 커밋 결과를 본다. DB 기준 잠금이라 앱 인스턴스가
늘어도 유효하고, 수집 저장량(주기당 수십 건)이 적어 전역 직렬화 비용은 무시할 수준이다.

검토한 대안:

- `@Version` 낙관적 잠금 + 재시도: 2의 덮어쓰기는 감지하지만 1(미그룹)은 해결하지 못한다.
- 잠금 전용 행에 비관적 잠금: H2에서도 동작하지만 스키마가 늘어난다.
- Redis 분산 잠금: DB 트랜잭션 밖의 잠금이라 커밋 후 해제를 별도로 보장해야 한다. 메서드 안 `finally`에서
  풀면 커밋 전에 해제돼 같은 경합이 다시 생긴다. TTL보다 트랜잭션이 길면 잠금이 조용히 풀리고, OCI 소형
  인스턴스에 인프라와 장애 지점이 늘어난다. 쓰기 주체가 수집 작업 두 개뿐이고 경합이 드물며 지킬 대상이
  PostgreSQL 데이터 정합성이므로 같은 DB의 트랜잭션 잠금을 택했다. 다수 사용자가 같은 자원에 몰려
  처리량·빠른 실패가 중요한 경우(예: 좌석 예약)에는 Redis가 맞을 수 있으며, 그때도 DB 고유 제약을 최종
  방어선으로 둔다.

**검증.** 같은 테스트가 수정 전 2건 모두 실패, 수정 후 통과. 반복 3회 통과. 전체 backend 테스트 통과.
저장소 CI는 Vercel 배포만 실행하므로 이 테스트는 Docker가 있는 로컬에서 실행한다.

## B. 같은 출처 중복 실행 (보류, 2026-10-20)

**판단.** 현재 운영은 OCI 서버 한 대의 앱 스케줄러만 수집한다. 스케줄러는 `fixedDelay` 단일 스레드라 자기 자신과
겹치지 않고, 홈 수집기는 운영하지 않으며 운영 수신 API도 꺼져 있다. 같은 출처가 동시에 수집될 경로가 없어
지금 구현하지 않는다. 겹치더라도 데이터는 고유 제약과 작업 A의 잠금으로 보호되고, 남는 피해는 출처 사이트에
대한 요청 증가다.

**재개 조건과 방향.**

- 홈 수집기 운영을 시작할 때: 출처 담당을 설정으로 고정하고, 수신 API가 앱 스케줄러가 수집 중인 출처를 거부한다.
  서버 1대·수집기 1개 구성에는 이것으로 충분하다. 수집기 이중 실행은 `up -d`만 상시 실행에 쓰는 운영 수칙으로 막는다.
- 서버·수집기가 여러 대가 되거나 담당을 자동으로 넘겨받아야 할 때: 출처별 DB 리스(TTL)와 결과 전송 시
  리스 토큰 검증(fencing token)을 검토한다.
- 검토 후 제외: 로컬 수집기 파일 잠금. 수집기는 읽기 전용 컨테이너의 컨테이너별 `/tmp`만 쓸 수 있어
  `up -d`와 `run --rm`처럼 다른 컨테이너끼리는 잠금을 공유하지 못한다.

## C-1. 운영 지표 (2026-10-20)

**목적.** 로그만으로는 수집 실패율·응답 시간·데이터 증가량에 답할 수 없다. C-2·C-3과 작업 A의
"잠금 대기 비용은 무시할 수준" 같은 판단에 수치 근거를 만든다.

**구성.** Actuator + Micrometer + Prometheus 출력 형식. 관리 포트 `8081`을 분리하고 `health`(상세 숨김)·`metrics`·
`prometheus`만 노출한다. 지표 목록과 조회 방법은 `docs/06` 운영 지표 확인을 따른다.

- 저장 결과(created·updated·skipped)와 필드 확보율은 커밋 후에만 반영해 롤백된 배치를 수집량으로 세지 않는다.
- 태그 값은 출처 코드·결과 같은 고정값만 쓴다. 원격 수신의 지원하지 않는 출처 이름은 `unknown`으로 묶는다.
- 그룹화 잠금은 트랜잭션당 한 번만 DB에 요청하고 그 대기 시간만 기록한다. 같은 트랜잭션의 재호출까지 세면
  0에 가까운 표본이 섞여 평균을 왜곡한다.

**진행 중 발견.**

- 없는 경로 요청이 전역 예외 처리에서 500으로 응답하고 원인을 남기지 않았다. 404 `NOT_FOUND`로 바꾸고,
  예상하지 못한 오류는 응답에 내부 정보를 숨긴 채 서버 로그에 원인을 남긴다.
- Prometheus는 gauge 이름의 `_total` 접미사를 제거한다. 저장 건수 지표를 `pickdeal.deals.stored`로 정했다.
- Prometheus 출력은 히스토그램과 앱 계산 백분위를 함께 내보내지 않는다. 히스토그램만 남기고 p95는 Prometheus
  서버에서 계산한다. Prometheus 서버가 없는 지금은 `curl`로 p95를 바로 읽을 수 없으며, C-3의 백분위는 k6가 계산한다.
- 테스트 `application.yml`이 같은 이름의 운영 설정 파일을 통째로 가린다. 노출 범위를 `management.yml`로 분리해
  운영·테스트가 같은 파일을 가져오게 했다. 가져온 파일이 가져오는 파일보다 우선하므로 포트·주소는 각 파일에 둔다.
- Spring Boot 테스트는 기본으로 지표 내보내기를 끈다. 노출 검증 테스트에만 `@AutoConfigureMetrics`를 붙였다.

**검증.**

- 관리 포트에서 허용 엔드포인트만 200, `env`·`heapdump`·`loggers`·`beans`는 404, API 포트의 actuator와 없는 경로는 404.
- 수집 결과·마지막 성공 시각·수신 결과·커밋 후 집계를 테스트로 확인했다.
- PostgreSQL 동시성 테스트에서 잠금 대기 지표가 트랜잭션당 한 번(2건) 기록되고 뒤 트랜잭션 대기가 1초를 넘는 것을 확인했다. 3회 반복 통과.
- 로컬 PostgreSQL로 앱을 기동해 `127.0.0.1:8081`에서만 응답하고 지표가 출력되는 것을 확인했다(수집 스케줄러는 끔).
- 운영과 같은 형태의 일회성 Compose(compose 프로필, tmpfs PostgreSQL, 호스트 `127.0.0.1` 포트 연결)로 이미지를 빌드해
  Flyway·validate 기동, 관리 포트의 호스트 접근, 호스트 바인딩이 `127.0.0.1`뿐임, API 포트의 actuator 404를 확인했다.
- 미검증: 실제 OCI 반영과 실수집 지표 값(실수집 미실행).

## C-1+. 지표 저장과 대시보드 (2026-10-22)

**목적.** C-1의 지표는 앱 시작 이후 누적값이라 추이와 p95를 볼 수 없다. Prometheus로 시간별로 저장하고
Grafana 대시보드로 본다. 구성과 운영 절차는 `docs/06` 지표 저장과 대시보드를 따른다.

**판단.**

- 자원: 2026-10-21 운영 실측 available 4.8GiB. swap이 없어 상한을 반드시 둔다. 상한은 아래 로컬 실측으로 정했다.
- 수집 간격 60초: 30초는 같은 값을 두 배로 기록할 뿐이고, 2분 이상은 5분 staleness로 그래프가 끊길 수 있다.
- 배치: 같은 `compose.yml`의 프로필. Prometheus가 Compose 내부 이름 `backend:8081`로 수집하므로 지표 포트를 더 열지 않는다.
  프로필을 끄면 기존 배포와 같다.
- 이미지: Prometheus는 LTS 계열 `v3.13.4`, Grafana는 `grafana/grafana:13.2.3`. `grafana/grafana-oss`는 2026-06 이후 갱신이
  없어 쓰지 않는다. 둘 다 ARM64 이미지를 제공한다. 공개 직후 버전(하루 전 `v3.13.5`)은 피했다.
- Grafana 설정은 provisioning 파일로 관리해 볼륨을 잃어도 대시보드가 복구되고 저장소에서 리뷰된다.
- 알림은 채널 결정(roadmap) 전까지 두지 않는다.

**진행 중 발견.**

- Compose의 필수 변수 표기 `${VAR:?}`는 **프로필이 꺼진 서비스까지 해석**해 실패한다. Grafana 비밀번호를 이렇게 두면
  모니터링을 쓰지 않는 기존 배포의 `docker compose up`도 실패한다. 컨테이너 시작 시 검사(비어 있거나 `admin`이면 종료)로 바꿨다.
- Grafana 13의 실제 메모리가 예상(100~200MB)보다 컸다. 로컬 실측에서 프로세스 메모리(anon)가 시작 직후 약 245MiB,
  대시보드 사용 후 최대 약 380MiB였고, 384MiB 상한에서는 상한 도달(`memory.events`의 max)이 2만 회 이상 반복됐다.
  상한을 640MiB로 늘리고 `GOMEMLIMIT=480MiB`로 Go 런타임이 먼저 회수하게 하자 대시보드 사용 중에도 약 240MiB로 유지됐다.
  Prometheus는 약 34MiB라 512MiB에서 256MiB로 줄였다. 상한 합은 계획과 같은 약 3.4GiB다.
- 모든 값이 0인 시계열은 Grafana 자동 축이 무의미한 눈금(예: 1.67분)을 만든다. 잠금 대기 패널은 0~1초를 기본 범위로 둔다.
- 데이터가 없는 stat 패널이 기본 임계값 색(초록)으로 'No data'를 표시해 정상처럼 보였다. 기본 단계를 중립색으로,
  0 이상을 초록으로 나누고 '수집 기록 없음'으로 표시한다.

**검증 (로컬, 운영과 같은 compose.yml을 별도 프로젝트명·포트로 실행 후 정리).**

- `promtool check config` 통과. 프로필 없이 해석하면 backend·PostgreSQL만, 프로필을 켜면 4개 서비스.
- Prometheus 수집 대상 `backend:8081` 상태 up, 간격 1m, 오류 없음.
- Grafana: 데이터 소스·대시보드(17개 패널) 자동 등록, 데이터 소스 연결 정상, 비로그인 API와 회원가입 401.
- 대시보드의 PromQL 21개 모두 오류 없이 실행. API 호출 후 p95 패널 값 확인(빈 DB 로컬 값이라 성능 근거는 아님).
- 비밀번호가 비어 있거나 `admin`이면 Grafana가 시작하지 않음. 비밀번호 변경 명령(`grafana cli admin reset-admin-password`) 존재 확인.
- 포트는 모두 호스트 `127.0.0.1`에만 연결. PostgreSQL은 호스트 포트 없음.
- 대시보드 JSON 수정이 Grafana 재시작 없이 반영됨.
- 미검증: OCI(ARM64) 반영과 실제 메모리, 실수집 데이터가 있는 수집 패널(실수집 미실행).
