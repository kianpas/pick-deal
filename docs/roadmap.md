# PickDeal 로드맵

> 최초 작성: 2026-08-20 · 최근 갱신: 2026-09-05
> 이 문서는 **현재 상태, 확정 결정, 다음 작업과 완료 조건**만 관리한다. 상세 계약은 `docs/01~06`, 판단 근거는 `docs/notes/`와 `docs/adr/`를 따른다.

## 1. 제품 방향

PickDeal은 여러 커뮤니티에 흩어진 핫딜을 한곳에 모으고, 출처와 관심·제외 키워드로 소음을 줄이는 개인용 서비스다. 같은 구매 대상으로 강하게 판정된 다른 출처의 게시글은 대표 카드로 묶되 원본과 출처별 관측 정보는 보존한다.

현재는 단일 사용자 MVP다. 실제 운영 데이터가 없는 기능과 인프라를 미리 완성하지 않는다.

## 2. 현재 상태

- Next.js 목록·상세·키워드 설정과 데스크톱 사이드바 출처 설정이 Spring Boot API에 연결돼 있다.
- 퀘이사존과 루리웹을 20분 fixed-delay로 수집한다.
- `(source_id, external_id)`로 동일 출처 중복 저장을 막고 재수집 시 관측값을 갱신한다.
- 신규 Deal에 한해 제한적으로 상세를 조회해 판매몰 이름과 상품 URL을 저장한다.
- 보수적인 교차 출처 DealGroup 연결과 대표 목록·출처별 상세 UI가 구현돼 있다.
- 로컬 PostgreSQL과 `ddl-auto: update`를 사용한다. Docker, Flyway, 운영 프로필과 실제 배포는 아직 없다.
- 인증 없이 고정 `user_id = 1`을 사용하므로 현재 쓰기 API를 공개 인터넷에 그대로 노출하면 안 된다.

## 4. 확정 결정

### 데이터와 수집

- 출처는 게시 커뮤니티, 판매처는 실제 쇼핑몰이다.
- `originalUrl`은 커뮤니티 원문, `productUrl`은 원문이 제공한 상품·행사 링크다.
- HTML 전체와 이미지는 저장하지 않고 테스트에 필요한 HTML fixture와 원격 이미지 URL만 저장한다.
- 상품 URL이 없는 과거 Deal의 상세 backfill은 요청 비용 대비 가치가 낮아 하지 않는다.
- 댓글 수는 반응량이며 긍정 평가로 해석하거나 추천·정렬에 사용하지 않는다.
- 새 출처 추가 범위는 기본적으로 `docs/05`의 출처 표, 해당 출처 코드, 테스트 fixture다.

### 교차 출처 그룹

- 원본 Deal은 삭제하거나 병합하지 않고 그룹으로 연결한다.
- 자동 그룹 조건은 `판매처·가격 일치 AND (상품 URL 일치 OR 제목 정규화 해시 일치)`다.
- URL 단독 일치, 유사도·점수 기반 판정, tracking parameter 제거, 상품 ID와 embedding은 사용하지 않는다.
- 애매하면 합치지 않는다. 실제 오탐·미탐 사례가 쌓인 뒤 규칙을 조정한다.
- 행사 재시작 판정, 시간 제한과 자동 그룹 분리는 현재 범위가 아니다.

### 의도적으로 도입하지 않는 것

- Redis, 메시지 큐, 별도 collector worker
- Kubernetes, microservices, CQRS, 범용 crawler DSL
- 인증·멀티유저 전체 구현
- 가격 이력, canonical 상품 모델, 별도 Shop 엔티티

이 항목은 운영에서 구체적인 필요가 확인될 때만 다시 검토한다.

## 5. 다음 작업 — 11. 상시 운영 준비 및 최초 배포

작업 11은 현재 코드를 그대로 서버에 올리는 일이 아니라, 작은 품질 정리와 배포 기반을 마련한 뒤 실제 환경에서 수집을 검증하는 작업이다.

### 11-1. 배포 전 화면·품질 정리

- 프론트 lint 오류를 없앤다.
- 더 보기 후 출처를 숨겼을 때 이전 클라이언트 목록과 페이지 상태가 남지 않게 한다.
- 현재 `collectedAt`을 “마지막 수집”으로 오해하게 하는 표시를 바로잡는다.
- 실데이터에 연결되지 않은 쇼핑몰·알림·AI 요약 UI는 숨기거나 데모임을 명확히 한다.
- 모바일에서 출처 설정을 제공할지, 데스크톱 전용으로 둘지 결정한다.

완료 조건:

- frontend lint와 build가 통과한다.
- 출처 변경 시 첫 페이지·더 보기 결과가 같은 설정을 반영한다.
- 미구현 기능이 동작하는 기능처럼 보이지 않는다.

### 11-2. 배포 기반

- Dockerfile과 필요한 Compose 구성을 작성한다.
- local/prod 설정을 분리하고 운영에서 샘플 Seed를 끈다.
- Flyway 기준 스키마를 도입하고 운영에서는 `ddl-auto: validate`를 사용한다.
- 실제 프론트 도메인의 CORS와 HTTPS를 설정한다.
- 인증 없는 설정·내부 쓰기 API의 접근 범위를 정한다. 회원가입 전체 구현은 전제하지 않는다.
- PostgreSQL 위치를 결정한다.
  - OCI 같은 서버의 별도 DB 컨테이너와 영속 볼륨
  - 또는 Supabase PostgreSQL
- 선택한 DB의 백업과 복구 절차를 확인한다.
- health check와 최소 운영 로그를 준비한다.

완료 조건:

- 운영 설정에 비밀번호나 키를 커밋하지 않는다.
- DB와 backend 내부 포트를 불필요하게 공개하지 않는다.
- 컨테이너 재기동 후 데이터가 유지된다.
- 비인가 사용자가 개인 설정과 내부 등록 API를 변경할 수 없다.

### 11-3. 최초 배포와 실환경 확인

- frontend는 Vercel, backend는 OCI를 기본 구성으로 한다. frontend까지 OCI에 배포할 필요가 생기면 별도로 결정한다.
- backend 인스턴스는 하나만 실행해 scheduler 중복 실행을 막는다.
- 실제 프론트 브라우저에서 목록·상세·키워드·출처 설정을 확인한다.
- OCI 네트워크에서 출처별 수집을 한 번 실행해 응답·파싱·저장 결과와 요청 상한을 확인한다.
- 신규 딜이 없는 정상 회차와 수집 실패를 로그에서 구분할 수 있는지 확인한다.

완료 조건:

- HTTPS 환경에서 frontend와 API가 정상 연결된다.
- 두 출처 수집과 DB upsert가 성공한다.
- scheduler가 한 인스턴스에서만 실행된다.
- 백업 파일 생성 또는 관리형 DB 백업 정책을 확인하고 복구 방법을 기록한다.

## 6. 배포 후 운영 데이터로 판단할 것

다음은 배포 선행조건이 아니다. 일정 기간 실제 데이터를 관찰한 뒤 필요한 항목만 작업으로 올린다.

- 하루 신규 Deal 수, 수집 시간, timeout과 파서 실패 빈도
- 가격·판매몰·상품 URL·댓글 수 확보율
- 상세 요청 수와 성공 수, DB의 상품 URL 보유율
- DealGroup 오탐·미탐과 대표 게시글 상태 불일치
- 전체 Deal 메모리 처리의 응답 시간과 조회 행 수
- 수집 트랜잭션이 HTTP 지연이나 저장 실패에 미치는 영향
- 관심/제외 키워드와 출처 숨김의 실제 사용성

병목이 확인되면 그룹 단위 API 계약을 유지하면서 DB 페이지 처리, 수집 트랜잭션 분리, 필요 시 worker·Redis를 순서대로 검토한다.

## 7. 이후 방향

- **알림**: 상시 수집이 안정된 뒤 한 채널만 선택해 구현한다.
- **AI 댓글 요약**: 댓글 원문 확보 가능성과 요청·저장 비용을 먼저 조사한다.
- **개인화**: 읽음·관심 없음 등 실제 사용 중 반복되는 불편이 확인되면 우선한다.
- **멀티유저**: 공개 서비스 전환이 결정되면 인증과 사용자별 데이터 격리를 별도 마일스톤으로 설계한다.
